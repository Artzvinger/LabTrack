# LabTrack

Fullstack-приложение для учёта лабораторных образцов.

LabTrack позволяет просматривать образцы, отслеживать их статус и управлять доступом к данным в зависимости от роли пользователя и его лаборатории.

## Возможности

- Авторизация и управление пользовательской сессией
- Личный кабинет: редактирование ФИО и email, смена пароля
- Список образцов: номер, пациент, статус, лаборатория, дата получения
- Поиск по ФИО пациента и номеру образца
- Фильтрация по статусу, сортировка по датам, пагинация
- Сводка по статусам над таблицей
- Просмотр подробной информации об образце
- Смена статуса образца из карточки (в пределах своей лаборатории)
- Заметки врача: анамнез и заключение по пациенту
- Разграничение доступа между лабораториями
- Валидация данных на frontend и backend
- API-тесты: авторизация, права доступа, поиск, счётчики

## Технологии

**Frontend:** React, TypeScript, Vite, React Router, React Hook Form, Zod

**Backend:** Node.js, Express, TypeScript, Zod

**Database:** PostgreSQL, Drizzle ORM

**Testing:** Vitest, Supertest

**Infrastructure:** Docker, Docker Compose

## Запуск

Для запуска необходимы Docker и Docker Compose.

```bash
docker compose up -d --build
```

После запуска приложение доступно по адресам:

- Frontend: http://localhost:5173
- Backend: http://localhost:3000

При старте контейнера backend автоматически применяет миграции (`npm run db:migrate`) и заполняет базу тестовыми данными (`npm run db:seed`) — см. `server/Dockerfile`. Повторный запуск не дублирует данные, если они уже есть.

Остановка приложения:

```bash
docker compose down
```

### Запуск без Docker

Нужны Node.js 22+ и запущенный PostgreSQL 16 с базой `labtrack`.

В `server/.env` обязательны две переменные (файл не хранится в репозитории):

```dotenv
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/labtrack
SESSION_SECRET=любая-длинная-строка
```

Backend:

```bash
cd server
npm ci
npm run db:migrate
npm run db:seed
npm run dev
```

Frontend:

```bash
cd client
npm ci
npm run dev
```

Порт backend зафиксирован в коде (`server/src/server.ts`, `3000`). Клиент обращается к API на том же хосте, с которого открыта страница, поэтому приложение работает и по `localhost`, и по `127.0.0.1`, и по IP в локальной сети. Переопределить адрес можно переменной `VITE_API_URL` при сборке клиента.

Backend принимает CORS-запросы с `http://localhost:5173`, `http://127.0.0.1:5173` и любого loopback-порта. Дополнительные origin'ы (например, для доступа по IP) задаются через `CLIENT_ORIGINS` — список через запятую.

Пользователь лаборатории «Иммунология» (видит только образцы своей лаборатории):

- Login: `labuser2`

Образцы в сиде распределены между двумя лабораториями, поэтому `labuser1` и `labuser2` видят разные наборы. Сид можно запускать повторно: он добавляет только отсутствующие лаборатории и аккаунты.

Тестовые аккаунты предназначены только для локальной разработки. Эти же аккаунты показаны прямо на экране входа: клик по строке в блоке «Демо-доступ» подставляет логин и пароль в форму.

## Личный кабинет

У каждого пользователя есть страница `/profile`: ФИО и email с редактированием, смена пароля с проверкой текущего, роль, лаборатория, дата создания аккаунта и сводка по доступным образцам. После сохранения ФИО сразу обновляется в шапке приложения.

## Демо-данные

Сид создаёт 400 образцов — по 200 на каждую лабораторию: русские ФИО, номера вида `S-2026-0141` и статусы по свежести: новые образцы «Получен», старые «Завершён». Анамнез и заключение в сиде пустые — их заполняет врач в карточке. Данные детерминированы: повторный сид даёт те же записи.

## Архитектура

Frontend разделён на страницы, UI-компоненты, API-запросы, схемы валидации и TypeScript-типы.

Backend разделён на маршруты, middleware, работу с базой данных, схемы валидации и тесты.

Проверка авторизации и прав доступа выполняется на backend. Администратор имеет доступ ко всем образцам, а пользователь лаборатории — только к образцам своей лаборатории.

Для авторизации используются серверные сессии, хранящиеся в PostgreSQL. Пароли хранятся в виде bcrypt-хешей.

## Тестирование

Тесты обращаются к реальной базе, поэтому нужен запущенный PostgreSQL с применёнными миграциями и сидом (см. раздел «Запуск») и `DATABASE_URL` в `server/.env`.

```bash
cd server
npm run db:migrate
npm run db:seed
npm test
```

Тесты проверяют авторизацию, права доступа, поиск по ФИО и номеру, разбивку по статусам, личный кабинет (правка профиля и смена пароля) и формат ошибок API.
